## 一、工位/角色/工作流设计：跨会话协作从"能通信"变成"能@、能派单、能查在线"

Claude Code 本窗口连续多个版本，把"多个 Claude 会话互相发现、互相派单"从基础能力扩展成了完整的协作原语：

- **v2.1.224（2026-08-07）**：新增跨会话 `SendMessage`——任意机器上的 Claude Code 会话可通过 `ListAgents` 互相发现并留言（先支持 macOS/Linux）；同一版本还**移除了单会话 200 个 subagent 的派生总量上限**，长时间运行的会话不再因为累计派生过多而被拒绝新代理。
- **v2.1.232（2026-08-13）**：提示词中输入 `@` 即可提及另一会话，Claude 自动调用 `SendMessage`；会话重名时自动生成 `name-word-word` 变体，避免@出错对象。
- **v2.1.236（2026-08-19）**：新增 `notify_when_idle`——可请求另一会话"下次空闲时通知我一次"（一次性触发，不是轮询）。
- **v2.1.239（2026-08-21）**：Windows 平台补齐跨会话消息能力；`ListAgents`/`/list-agents` 首次把"活的队友（teammates）"和普通 subagent、其他会话一起列出（此前队友虽可达但列表里看不见）。

对"工位/角色/工作流设计"子领域的启发：这组更新的实质是把赛博工头方法论里"角色是可寻址实体、可以按名字派活"的理念，变成了 Claude Code 的平台原生能力——角色可以被@、按名字查在线状态、请求"忙完了通知我"，而不必再靠人工在多个窗口间切换盯进度。同一窗口内 v2.1.229（8-12）还给"同前缀的并行工位"加了错峰执行（可让后续代理命中缓存的公共前缀而不必重新付费读取，`CLAUDE_CODE_WORKFLOW_PREFIX_STAGGER_MS=0` 可关闭），直接影响多工位并行工作流的运行成本。

来源：[Claude Code Changelog](https://code.claude.com/docs/en/changelog)（v2.1.224、v2.1.229、v2.1.232、v2.1.236、v2.1.239 条目）

## 二、自动化与节奏：自托管运行环境 + 检查节奏改退避策略

- **`claude self-hosted-runner`（v2.1.224，2026-08-07，Team/Enterprise 计划）**：允许 Claude Code 的 web/mobile/desktop 会话运行在用户自己的机器或容器上，而不是只能由 Anthropic 云端承载；后续版本持续加固——v2.1.229（8-12）支持服务端下发的 hook，v2.1.238（8-20）新增收到终止信号后延迟关闭、为已连接会话争取收尾时间的选项。
- **后台/定时任务检查节奏调优**：v2.1.235（8-18）起，当后台任务让某个目标（Goal）等待超过 30 分钟，Claude 会主动介入检查；v2.1.239（8-21）把这个检查节奏改为**退避策略**——30 分钟、1 小时，之后每 2 小时一次，不再是固定 30 分钟死循环轮询，从 `--resume` 恢复会话时活跃 Goal 状态一并恢复。
- v2.1.234（8-17）新增"用量额度重置后自动续跑会话"（可在 `/config` 关闭），提升长跑任务的连续性。

对"自动化与节奏"子领域的启发：`self-hosted-runner` 是"云端负责调度触发、本地/自有基础设施负责实际算力与合规边界"这套分工范式的官方实现；退避式检查节奏则是"定时任务该多久查一次进度"这个具体调度问题在平台层面给出的默认答案，直接可作为设计自己 Routine 检查频率时的参考基线（不必一律死等固定间隔）。

来源：[Claude Code Changelog](https://code.claude.com/docs/en/changelog)（v2.1.224、v2.1.229、v2.1.234、v2.1.235、v2.1.238、v2.1.239 条目）

## 三、人工闸门与对外守门：高自主度会话的外部指令须先过人工关卡

**v2.1.224（2026-08-07）**新增 `crossSessionInbound` 与 `dialogExpiry` 设置：发给一个正以"绕过权限（bypassed permissions）"模式运行的会话的跨会话消息，会被**挂起等待人工批准**，而发给普通会话的消息则自动送达。

同一窗口起点、**v2.1.222（2026-08-04）**还把后台会话的默认行为改为"先 commit/push 保留工作成果、只有任务确实需要时才开草稿 PR"（而不是每次都发起 PR），并要求每次任务结束都必须报告工作成果落在哪里。

对"人工闸门与对外守门"子领域的启发：前者是一个非常具体的产品化案例——当某个工位处于高自主度运行状态时，外部指令必须先过人工关卡才能真正影响它，防止"自动化的会话"被另一个自动化会话悄悄改变行为，与赛博工头"人把最后一道关"直接对应；后者则是把"默认对外动作"收紧为"默认只留痕，发布与否留给人"，两条合在一起可作为"高自主度工位该配什么护栏"的最新工程参照。

来源：[Claude Code Changelog](https://code.claude.com/docs/en/changelog)（v2.1.222、v2.1.224 条目）

## 四、引擎迁移与不锁定：MCP 官方发布新路线图，把"传输统一+企业身份认证"列为优先方向

MCP（Model Context Protocol）官方博客于 **2026-08-22** 发布《The New MCP Roadmap》，由核心维护者联合社区制定，提出五个优先方向：智能体消息原语成熟化、**HTTP 原生传输统一**（降低"一个 MCP server 要为不同客户端各写一套"的摩擦）、**采用 DPoP / Workload Identity Federation 等标准的企业级身份认证**（替代"粘贴 API key、长期有效令牌"的做法）、改进工具调用结果与渐进式发现、改进 SDK 开发体验。

对"引擎迁移与不锁定"子领域的启发：传输统一与标准化身份认证这两项，直接服务于"降低对单一厂商实现细节的依赖、提升跨引擎可移植性"——是本窗口内在"不锁定"这个主题上最实、最新的一条可验证消息，可作为向客户解释"为什么组织资产要以 MCP 这类开放协议为准而不是绑死某家厂商私有接口"的最新依据。

来源：[MCP Blog · The New MCP Roadmap](https://blog.modelcontextprotocol.io/posts/mcp-roadmap/)（2026-08-22，已直接核实原文）
