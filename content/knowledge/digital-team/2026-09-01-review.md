## 一、工位/角色/工作流设计：Claude Code 把 Agent Teams 跨会话协作的边缘故障逐一打磨

Claude Code 本窗口连续发布的版本里，多条集中在"让多个会话/子代理之间的协作更可靠"这个具体问题上：

- **v2.1.243（2026-08-24～25）**：新增 `CLAUDE_CODE_SUBAGENT_MODEL` 作为子代理的**默认**模型（而非强制覆盖）——Agent 定义文件里显式写的 `model:` 字段优先级更高，不会被这个环境变量覆盖；`/cost` 增加逐会话缓存命中率统计。
- **v2.1.248（2026-08-27）**：跨会话消息能力（`SendMessage`/`ListAgents`）在 Bedrock/Vertex/Foundry 三种企业部署方式上打通，此前仅原生 API 支持。
- **v2.1.251（2026-08-28）**：修复一批 Agent Teams 协作细节——队友的最终答案此前会显示为"空的可用通知"，改为通过 idle 通知正常送达；修复后台子代理无法回复"未命名"兄弟/父代理消息的问题；`SendMessage` 从子代理转发到另一会话时，回复能正确传回发起的父会话对话；新增对过大而无法投递的跨会话消息的显式拒绝（此前会静默丢弃）。

对"工位/角色/工作流设计"子领域的启发：这批修复没有引入新概念，而是把上期综述收录的"角色可寻址、可@、可派单"这套跨会话协作原语，从"能用"打磨到"边缘情况也可靠"——队友消息不再静默丢失、模型选择优先级更明确、企业云部署也能用同一套协作能力。这正是赛博工头方法论里"角色书写清楚不够，还要保证消息真的能送达"这一环节的具体工程参照。

来源：[Claude Code Changelog](https://code.claude.com/docs/en/changelog)（v2.1.243、v2.1.248、v2.1.251 条目）

## 二、人工闸门与对外守门：三大编码 Agent 同期收紧"默认关闭、按需放行"式闸门

**Claude Code v2.1.248（2026-08-27）**新增 `--restricted` 启动参数（或环境变量 `CLAUDE_CODE_RESTRICTED=1`）——受限模式下移除内置命令与代码运行工具，适合把会话限定在纯对话/只读场景。

同一窗口内，**Gemini CLI**：v0.57.0 正式版（08-25）加入上下文感知重试与多轮请求回滚；nightly 版本 08-27 修复了 MCP OAuth 元数据发现流程中的一处 SSRF 漏洞；nightly 版本 08-29 把工作区信任检查改为 **fail-closed**（默认不信任、需显式确认），并在受限模式下对 `mcpServers` 配置做过滤。**Codex CLI** rust-v0.151.0（08-29）新增"扩展可在工具调用结果送回模型前先检查/修改"的拦截点，相当于给工具调用结果加了一道可编程的审查关卡；rust-v0.150.0（08-26）则是任务管理侧的更新——支持用 `@` 引用任务、AI 自动生成任务标题。

对"人工闸门与对外守门"子领域的启发：三家主流编码 Agent 在同一周内分别从不同角度收紧了闸门——Claude Code 给了一个"整体降权"的开关，Gemini CLI 把信任判断的默认值从"信任"改成"不信任"，Codex CLI 则在工具调用结果这个具体节点插入了可编程检查点。三条合在一起印证了"人工闸门与对外守门"方法论里的一个具体落地方向：闸门不该只停留在文档约定的行为红线，而应尽量做成运行时**默认关闭、白名单显式放行**的强制机制——这与赛博工头给工位设计审批闸门时"别信任任何默认状态"的原则高度同构。
